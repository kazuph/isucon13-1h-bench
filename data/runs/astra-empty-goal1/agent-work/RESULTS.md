# ISUCON 改善結果

CONDITIONS.md と manual/ を確認し、指定された3台だけをサービス提供に利用した。

| 計測 | スコア | 結果 |
|---|---:|---|
| 初期実装 | 7,830 | pass |
| 改善後・再起動前 | 175,666 | pass |
| 全3台再起動後 | 173,838 | pass |

再起動後は初期の **22.20倍**、再起動前の **98.96%**。再起動後の計測終了は 2026-11-17T02:22:11.473Z。

## 主な変更

- SQL の索引追加、統計集約、モデレーションの一括削除、一覧取得の一括読み込み。
- リクエスト内でユーザー・配信情報を再利用。プロセスをまたぐ可変データキャッシュは使用していない。
- 画像ハッシュの生成列保存、ETag と304応答、更新処理のユーザー単位ロック。
- 予約枠の範囲走査と必要なロックを維持し、重複した読み出しを削減。
- DNS の名前索引、A レコード TTL 60秒、正の問い合わせキャッシュ。負のキャッシュ・パケットキャッシュは無効。
- s1 は入口・DNS・登録・初期化、s2 は通常 API と DNS DB、s3 はアプリ DB。

具体的な配置と再ビルド方法は [deploy/README.md](deploy/README.md) を参照。

## 検証したこと

- Go のビルド、`go test ./...`（元リポジトリに Go テストはなし）、`go vet ./...`、nginx 設定検査が成功。
- `tests/smoke.py` で、問い合わせ済みの未登録 DNS 名が登録直後に解決できること、s2 の画像更新が両アプリで反映されること、ETag の200/304応答を確認。
- 全3台で `sudo reboot` を実行。systemd の起動時刻が更新され、必要サービスが自動起動。
- 全12アプリテーブルと DNS の records/domains のチェックサムが再起動前後で完全一致。
- 再起動後、API でユーザーと更新画像の保持を確認してからベンチマークを実行し pass。
- bcrypt のアルゴリズム・コストを維持。DB のコミット時永続化を維持。初期化応答は `language` と `lang` の両方を返す。

ベンチマークには初期実装でも見られたコメント報告関連等の一般エラーが残る。最終実行にも一般エラーと1件のタイムアウトが記録されたが、ベンチマーカーの判定は pass。スパム投稿の expected:400 / actual:201 は提供マニュアルに減点対象外との記載がある。

生ログは `logs/bench-*.log`、永続化検証は `logs/checksum-*.txt`、起動状態は `logs/state-*.txt` に保存。最終ベンチマークでデータは再度初期化されている。
