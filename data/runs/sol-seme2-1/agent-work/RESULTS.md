# ISUPipe 改善結果

CONDITIONS.md と manual/ の当日マニュアル・アプリケーション仕様を確認して実施した。

最終計測: **249,291点、成功**。初期実装4,385点の **約56.9倍**。3台すべての再起動後、最初のベンチマークで成功した。

## 構成

- s1 (10.99.0.11): nginx の TLS 終端・静的配信、Go 製 authoritative DNS。
- s2 (10.99.0.12): Go アプリ。GET API はメモリの参照モデルから応答。
- s3 (10.99.0.13): MySQL。すべての更新を保存し、初期化・起動時に参照モデルを再構築。

コメント、リアクション、視聴履歴、アイコン、報告は単一の SQL 書き込みを完了してから参照モデルへ反映する。単一書き込みがMySQLのデッドロックでロールバックされた場合は、上限付きで再試行する。登録・予約・モデレーションはトランザクションを維持。予約枠の排他と bcrypt の方式・コストは維持した。モデレーションで削除するコメントは、既存の報告から再起動後にも参照できるよう archived_livecomments に保存する。

DNS は実在レコードをメモリで照会し、不明な名前には NXDOMAIN を返す。登録時と初期化時に同期更新し、再起動時は DB から読み込む。A/AAAA/NS/SOA/TXT に対応する。

生の結果は baseline.log と run*.log に保存。DNS 参照先の切り替え、アプリ起動完了前のベンチ開始による失敗も記録に含む。最終結果は final-bench.log。開始 2026-11-17T05:02:18.280Z、終了 2026-11-17T05:03:25.238Z。

再起動検証では、この環境でMACアドレスが変わるため、旧MAC宛ての最初のDNS要求が OTHERHOST として破棄されることをパケット採取で確認した。3台とも、自分に割り当て済みのIPv4アドレスについて起動時にARPを通知する oneshot service を追加。修正後、全台再起動後の最初のDNS要求は新MAC宛てに届き、即時応答することを確認した。採取記録は checks/dns-startup-trace.log。採取用serviceは検証後に無効化・削除した。

## 検証

- 実際のベンチマーカーによる整合性チェック・負荷走行。
- 最終走行後も、上位15ユーザーと15配信について API と SQL の順位・集計値を照合。API/DBの投げ銭合計は249,301で一致。スコアはマニュアルに従いベンチ計測値249,291を採用。
- Go のスパム判定と MySQL LIKE を252組（日本語、絵文字、ワイルドカード、エスケープを含む）で照合。
- go vet ./... を通過。
- 153個の API レスポンスをハッシュ化し、アプリ再起動前後で一致を確認。
- 3台すべてを sudo reboot し、153個の API レスポンスの一致を確認。MySQL の innodb_flush_log_at_trx_commit=2 設定を含む正常再起動での保存・復元を検証した。

## ファイル

- network/announce.go と config/isupipe-arp-announce@.service: 起動時の自IPv4アドレスのARP通知。
- app/: デプロイした Go ソース（旧ハンドラーも参照用に残る。main.go のルート定義が実際の処理を指定）。
- config/: nginx、DNS service、環境変数、MySQL 設定、初期化SQL、追加テーブル。
- indexes.sql: 追加インデックス。icons.user_id は最終構成で UNIQUE に変更した。
- checks/: SQL 照合、LIKE 比較テスト、再起動前後の API ハッシュ比較。
- original/: 初期実装と SQL のバックアップ。
